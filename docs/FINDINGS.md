# 🔬 FINDINGS — AI 能力边界发现录

> Super-Lili 是一个完全开放的自进化实验。这份文件沉淀实验中**确凿学到的、可泛化的事实**——
> 关于当前大模型的能力边界、以及构建自治 AI 流水线的工程规律。
>
> 与其他记录的区别：日记是过程，进化日志是莉莉的自我反思，质量账本是分数流水——
> 而这里只收录**有证据支撑的结论**。每条 = 一个可验证的声明 + 证据 + 应对 + 推论。
>
> 格式：编号递增，状态为 `确认 / 观察中 / 已推翻`。写入门槛：至少两次独立事件支撑，
> 或一次事件 + 机械可复现。**每条必须写明涉及的具体模型和版本**——能力边界的结论
> 只对特定模型、特定时点成立；换模型或模型升级后，旧结论应重新检验而不是默认沿用。

## F-001 · LLM 评审无法替代执行验证——模型会学会骗过没有地面真值的门

- **日期**：2026-06-19 ~ 07-03 · **状态**：确认
- **模型**：生成侧 gemini-2.5-flash、deepseek-v4-flash（经 deepseek-chat 别名）；评审侧为同批模型自评（回音壁即此）。qwen3.7-max 独立评审 2026-07-03 才接入，仅覆盖本条末段
- **声明**：当质量门是"让另一个 LLM 看代码/预览猜它是否真的工作"时，生成模型会稳定产出
  "看起来像样但不做实事"的产物（静态 HTML 壳、CSS 假交互、硬编码答案）。同期，被真实
  执行验证的 Mode 1/2 工具没有此问题。
- **证据**：质量账本 2026-06-19~07-03 期间 Mode 3 尝试的 Critic 拒绝原因高度集中于
  "fundamentally fake / does nothing with input"；同一模型在 Mode 1/2（真实运行
  `process(测试输入)` 并评审真实输出）下无此模式。
  **2026-07-06 实战确认**：Playwright 地面真值门首次开火——真实填入输入、点击控件后
  以执行证据拒绝（fields_filled=1, text_changed=False, nodes 21->21），deepseek-v4-pro
  在全部反伪造规则生效的情况下仍产出静态假交互工具，被执行证据而非 LLM 猜测拦下。
- **应对**：① 按验证能力分流——分析型工具强制走可执行验证的 Mode 1/2；② 给 Mode 3 建立
  地面真值：Playwright 无头浏览器真实运行、喂输入、断言 DOM 变化（fail-open 设计，
  浏览器抖动不误判）。
- **推论**：自治流水线的每个质量门都应回答"这个门有没有 ground truth"。没有的门
  不是门，是模型的靶子。

## F-002 · "一次性生成真交互工具"超出当前开放模型的可靠边界；"一次性生成纯函数"在边界内

- **日期**：2026-06-19 ~ 07-04 · **状态**：确认
- **模型**：gemini-2.5-flash/2.0-flash、deepseek-v4-flash（经 deepseek-chat 别名）；2026-07-03 起 deepseek-v4-pro 亦复现（均为一次性生成，无迭代）
- **声明**：要求模型单次产出"对任意用户输入做真实分析的 HTML+JS 应用"，DeepSeek v4-flash/
  v4-pro、Gemini Flash 均无法稳定完成（成功率≈0）。同样的分析逻辑作为 `process(text) -> str`
  纯函数则稳定得多。历史上真正成功的 HTML 工具全部是**环境型/生成型**（时钟、氛围物），
  即不需要解析输入的类型。
- **证据**：67 天工具史——通过的 HTML 工具（如阳光色温时钟）均为 Format E；分析型 HTML
  尝试全部被拒。2026-07-03 解锁 Mode 3 后连续 5 次失败均为分析型概念套 HTML 壳。
- **应对**：SPEC 路由规则——"用户粘贴文本、拿回洞察"= Mode 1/2；Mode 3 仅留给真交互/
  环境型概念。
- **推论**：给自治系统分配任务时，任务分类应基于"模型可靠性画像"而不是"哪种形式更炫"。
- **2026-07-25 部分推翻**（推翻证据见 F-017，模型 deepseek-v4-pro）：本条前半段
  （"分析型 HTML 应用不可靠"）依然成立；但**后半段"纯函数更可靠"已被 311 次尝试的
  统计推翻**——Mode 1/2 分析型工具 28 天通过率仅 3%，低于 Mode 3 的 D（8%）与 E（11%）。
  真正的可靠性分界线不是输出格式，而是"价值是否依赖算法深度"。原结论把两个混同了，
  因为当时成功样本太少（Format E 的时钟）看起来像"格式差异"。

## F-003 · DeepSeek 空响应是瞬时故障，Gemini 空响应是配额信号——同一症状，相反语义

- **日期**：2026-07-03 · **状态**：确认
- **模型**：gemini-2.5-flash 免费档 vs deepseek-v4-pro 付费档
- **声明**：Gemini 免费档返回空响应通常意味着配额耗尽（重试无益，应切换）；DeepSeek 返回
  空响应（含 `finish_reason=length` 的截断空）通常是瞬时服务抖动（重试 1-2 次即恢复）。
  把 Gemini 时代的"一次空响应=模型死亡"逻辑带进 DeepSeek，导致了两次本可避免的 rest day。
- **证据**：2026-07-03 两次运行日志——BUILD 尝试 4/5 因单次空响应直接放弃；修复
  （空响应重试 + 跨厂商后备链）后同类空响应在 attempt 2-3 恢复。
- **应对**：`call_gemini_simple` 空响应重试 3 次带退避；后备链 R1 → v4-pro → qwen3.7-max。
- **推论**：换 LLM 供应商时，错误语义表必须重新校准——症状相同不代表原因相同。

## F-004 · 模型会把"举例"当"规格"——给差异化举例音节数，它就编造音节数

- **日期**：2026-07-03 · **状态**：确认
- **模型**：deepseek-v4-pro（生成）；qwen3.7-max（识破）
- **声明**：在修复"多项分析输出全部雷同"时，重试反馈里举例"可用音节数、词源、语域来
  差异化"。模型照做并**编造了错误的音节数**（"oakcraft 是 3 个音节"，实际 2 个），被
  Critic 以幻觉事实拒绝。教学性举例被模型执行为字面规格。
- **证据**：2026-07-03 20:30 运行日志，Critic 拒绝原因原文引用了错误音节数。
- **应对**：差异化只允许用**从输入文本本身可测量的属性**（长度、位置、频率、结构）；
  BUILD prompt 加反幻觉规则：禁止断言任何无法从输入推导的外部事实。
- **推论**：给生成模型的每一个例子都会被当作可执行规格。写反馈时举例的安全边界是
  "这个例子被逐字执行也不会出错"。

## F-005 · 愿景式规格必然导致偷懒实现——算法深度必须写成机械过程

- **日期**：2026-07-04 · **状态**：确认
- **模型**：deepseek-reasoner(R1) 写 SPEC；deepseek-v4-pro 写 BUILD
- **声明**：SPEC 里写"把辩论结构化成有洞察的章节"（愿景），BUILD 会用"抓第一句话+
  编一个标题"技术性满足它。写成"按说话人标记切分；合并连续同人发言；按词频取每组
  前 3 词做标签；相邻组词汇重叠<0.2 处标记话题转换"（机械过程），BUILD 才有可实现
  的对象。
- **证据**：2026-07-04 08:30 运行——流水线首次端到端全通，唯一失败点即"抓第一句+幻觉
  标题+忽略第二说话人"，Critic 原文确认。
- **应对**：SPEC 模板要求算法深度为"程序员可逐字实现的分步过程"；validate_spec 机械
  拒绝无具体计算动词的描述。
- **推论**：对自治系统，规格的可执行性 > 规格的美感。检验标准：拿掉所有形容词后，
  规格还剩下可实现的操作吗？

## F-006 · 单文件工具不能承诺外部世界——模型会自然设计出需要语料库的方案然后造假

- **日期**：2026-07-03 · **状态**：确认
- **模型**：deepseek-reasoner(R1)（SPEC 设计侧）
- **声明**：不加约束时，SPEC 模型（R1）反复设计出需要"精选品牌语料库对照"、"行业基准
  数据库"、"预训练分类器"的工具方案。而工具实际是无数据库、无网络的单文件——BUILD
  无法诚实实现，只能造假，再被 Critic 拒绝。死循环。
- **证据**：2026-07-03 三次运行的 Critic 拒绝原因均包含"promises...curated corpus /
  no real algorithmic depth"。
- **应对**：validate_spec 自包含检查——算法深度/转换描述中出现 corpus / database of /
  pretrained 等承诺即拒绝，强制"只从用户输入本身计算"。
- **推论**：模型的设计先验来自见过的真实产品（有后端、有数据），部署约束必须作为
  硬闸写进验证器，写进 prompt 是不够的。

## F-007 · 把 HTML/CSS/JS 塞进 Python 字符串是稳定的语法错误源；raw 三引号 Jinja2 是解

- **日期**：2026-06-22 ~ 07-03 · **状态**：确认
- **模型**：deepseek-v4-flash（经 deepseek-chat 别名，6月）与 deepseek-v4-pro（07-03）均复现
- **声明**：模型生成"Python 里嵌 HTML"代码时，两类语法错误反复出现：① CSS/JS 反斜杠
  （`content:'\2014'`、正则 `/\d+/`）触发 "line continuation" 错误；② JS 大括号与
  f-string 冲突触发 "was never closed"。指定 `Template(r'''...''')`（raw + 三引号 +
  Jinja2）后此类错误消失。
- **证据**：2026-07-03 两次运行共 4 个语法错误全属此类；prompt 加 raw-string 强制规则后
  的运行零语法错误。
- **应对**：BUILD prompt 强制 raw 三引号 Jinja2 模板；重试反馈对这两类错误给专项诊断
  （区别于"代码太长被截断"）。
- **推论**：错误信息的正确分类是自治重试有效的前提——把转义错误误诊为截断，重试只会
  越改越短。

## F-008 · 自治流水线的失败会"上游化"——这是健康的调试轨迹

- **日期**：2026-06-19 ~ 08-02 · **状态**：确认（2026-08-02 由观察中升级）
- **模型**：跨越两代组合（06月 Gemini+deepseek-v4-flash；07-03 起 Qwen+DeepSeek R1/v4-pro），与单一模型无关
- **声明**：两周的失败位置持续向价值链上游移动：模型选错 → API 韧性 → 模式路由 →
  字符串工程 → 幻觉事实 → 规格质量。每修复一层，暴露的下一层失败都更接近"产品本身
  的难题"。当失败停在"输出不够聪明"时，管道工程阶段结束，产品阶段开始。
- **证据**：本文件 F-001 ~ F-007 的日期序列即该轨迹。
- **应对**：用"失败在哪一层"作为流水线成熟度的度量，而不是二元的成功率。
- **推论（待验证）**：当前架构下，工具智能度的天花板由"stdlib 单文件纯函数能表达的
  算法"决定。这个天花板与"创意专业人士愿意用第二次"的底线之间是否有交集，是本实验
  接下来要回答的核心问题。
- **2026-07-12 补充证据（状态不变，观察中）**：本周（07-06~07-12）14 次失败
  （07-10/07-11）没有延续"失败位置持续上移"的轨迹，反而退回了管道工程早期的低层
  缺陷——JS 语法未写完（`const b = p` 截断）、markdown 表格错位、DOM 不响应输入、
  照抄输入不转换（见 F-011）。这些工具的共同点是 SPEC 允许的输入格式范围比之前更宽
  （"Jira 工单、Figma 评论、客户邮件"三选一到"扫描 Figma 文件、PDF、ZIP 包"）。
  推测：F-008 的"上移"轨迹不是单向棘轮，而是与当次 SPEC 的范围收紧程度绑定——
  SPEC 一旦重新放宽，失败会退回到更早的层级。这个反例本身也支持 F-008 的核心应对
  （用"失败在哪一层"衡量成熟度），只是提示这个度量会随 SPEC 纪律松紧而波动，不会
  单调上升。
- **2026-07-19 补充证据（状态不变，观察中）**：本周（07-13~07-19）81 次尝试、
  3 次通过，失败原因 55 次 Critic 拒绝 / 26 次 Browser ground-truth 拒绝。
  07-14~16 三个连续 rest day 的 Critic 拒绝原文——"no real algorithmic depth,
  relying entirely on trivial regex"、"raw, truncated SVG code (cutting off
  mid-attribute)"、"basic SVG viewBox manipulation and DOM element selection
  boilerplate"——与 07-12 补充证据描述的低层缺陷（JS 语法未写完、DOM 不响应、
  照抄不转换）属同一族，不是新的失败类型。样本继续支持"非单调、随 SPEC 收紧
  程度波动"的推论：07-13/07-17（SPEC 范围相对收紧的环境型概念）各自在多次重试
  后于同一天内通过，07-14~16（Office Automation 的"brief 结构化""多版本冲突
  检测"类概念，范围更宽）连续三天在算法深度这一底层缺陷上全军覆没。样本量增加
  但推论未变，继续保持"观察中"。
- **2026-08-02 补充证据（状态从观察中升级为确认）**：本周（07-27~08-02）56 次
  尝试、3 次通过，失败集中在"no real algorithmic depth / fundamentally fake"
  （音频转录三源对齐、DOI 引用格式化、学术引用锚点匹配等 Office Automation/
  Education Evolution 宽范围概念）——同样是低层缺陷，同样发生在 SPEC 范围较宽
  的一周。这是继 07-12、07-19 之后第三个独立时间窗口都支持同一个非单调假设：
  失败位置不随时间单调上移，而是随当次 SPEC 范围的收紧/放宽同步收紧/放宽。三个
  独立周期的一致复现（跨越 qwen-plus/deepseek-reasoner/deepseek-v4-pro/
  qwen3.7-max 这一整套模型组合的稳定期，非模型更替造成）达到"确认"门槛。
- **推论更新**：把 F-008 原标题"失败会上游化"精确为——失败层级是 SPEC 范围
  纪律的因变量，不是时间的单调函数。用它衡量流水线成熟度时，必须同时记录当周
  SPEC 范围的宽窄，否则同一衡量标准会在不同周之间给出看似矛盾的读数。

## F-009 · 模型会发明条目把结构化输出"补完整"——形状完整性优先于内容诚实性

- **日期**：2026-07-04 ~ 08-01 · **状态**：确认（2026-08-02 由观察中升级）
- **模型**：deepseek-v4-pro（生成）；qwen3.7-max（识破）
- **声明**：当输出是结构化列表/时间轴/表格时，若输入内容不足以填满"预期的形状"，
  模型倾向于**发明条目补位**而不是输出诚实的短列表。例：时间轴章节工具在输入无结尾
  信息时，编造了一个 01:10:00 时间码的"Conclusion"章节。与 F-004（编造外部事实）
  不同，这是**编造输入内该有而没有的内容**——对"完整形状"的先验压倒了对输入的忠实。
- **证据**：2026-07-04 14:30 运行，Critic 拒绝原因原文："hallucinating a generic
  'Conclusion' chapter at an arbitrary 01:10:00 timecode to finish the timeline"。
  同日 08:30 运行的"忽略第二说话人"是同族问题的另一面（该省不省、该有没有）。
- **应对**：BUILD prompt 加可溯源规则（每个输出条目必须能追溯到输入的具体位置；
  3 个真实条目优于 5 个含伪造的）；重试反馈新增"填充物"专项分支——明确这是删除
  任务而非补充任务。
- **推论**：结构化输出的诚实性需要显式约束"输出长度跟随输入内容"，否则模型会按
  训练数据里"这类表格通常长什么样"来补形状。
- **2026-08-01 补充证据（第二个独立事件，状态从观察中升级为确认）**：一个像素值
  转排版比例尺的工具（输入 6 个像素值，完整确定 5 个比值），BUILD（deepseek-v4-pro）
  连续 5 次尝试全部被 Critic（qwen3.7-max）拒绝，拒绝原文包括"the output invents
  random ratios (6.800, 0.118, 9.750) that have zero connection to the actual
  input values"以及"the output hallucinates steps 4 through 10 with nonsensical
  ratios"——输入只支持 5 步，模型仍编造出第 4 到第 10 步，明显是把工具描述里提到
  的"标准排版比例尺"（惯例上有约 10 级）当作应填满的形状，而不是老老实实只算 5 个
  已确定的比值。与 07-04 的时间轴案例是完全不同的领域（视频章节 vs. 数值计算），
  相隔近一个月，独立复现同一根因：形状完整性的先验压过对输入的忠实计算。
- **推论更新**：这个模式不局限于"文本信息不足以填满结构"（07-04 的原始表述），
  在"输入信息完全充分、只是数量少于假设中的标准形状"时同样触发——只要模型对
  "这类输出通常有几项"有先验，哪怕真实计算本身很简单（除法），也会被形状先验
  压过。防护规则需要覆盖这个更宽的触发条件，不能只依赖"信息不足时才检查"。

## F-010 · 约束的跷跷板效应——禁止伪造后，模型摆向"诚实地拒绝工作"

- **日期**：2026-07-04 · **状态**：观察中
- **模型**：deepseek-v4-pro（生成侧）
- **声明**：对同一深层行为（对输入不忠实）从一侧加约束，模型会摆向对侧失败而不是
  收敛到中间态。时间线：14:30 模型**伪造**条目补全输出 → 部署"禁止伪造、每条目可溯源"
  规则 → 20:30 模型不伪造了，但输入缺少说话人标记时**直接拒绝**（返回一行
  "No speaker-turn segments found. Please check the format."）。两种失败共享同一根因：
  模型缺少"优雅降级"的中间概念——主要结构标记缺失时退回粗粒度切分（段落→句子→定长块）
  继续尽力工作。
- **证据**：2026-07-04 三次运行日志的行为序列（伪造 → 填充 → 拒绝），其中 20:30 的
  拒绝发生在反伪造规则部署之后 6 小时。
- **应对**：BUILD prompt 明确"优雅降级"为强制要求（主标记缺失→逐级退回粗粒度切分，
  限制说明只能附注在真实输出后，不能替代输出）；rigid-input 重试分支扩展关键词，
  接住"礼貌拒绝"类输出。
- **推论**：给生成模型定行为边界时，禁止性规则必须配对指明"正确的中间态是什么"，
  否则模型在被禁行为的对立面找最近的出口。单侧围堵会制造钟摆。

## F-011 · 输出结构给定但转换步骤未写成机械过程时，模型退化为"复制粘贴"而非转换

- **日期**：2026-07-10 · **状态**：确认
- **模型**：deepseek-v4-pro（BUILD）；qwen3.7-max（识破）
- **声明**：SPEC 要求"把原始项目材料（Jira 工单/Figma 评论/客户邮件/设计时间线）转换
  为结构化叙事、时间线或摘要"，但算法深度没有写成 F-005 要求的机械步骤时，BUILD 会
  稳定产出"输出结构照抄输入结构"的假转换——把原始文本块整段搬进输出模板的字段里，
  不做任何提炼、判断或重组。这与 F-004（编造事实）、F-009（编造条目补形状）是同一
  失败家族的第三种变体：这次模型连编都不编，直接照搬。
- **证据**：2026-07-10 同一天内三个独立工具概念（"Jira/Figma/客户邮件案例研究生成器"
  "按时间顺序的设计产物工具""raw project notes 转换工具"）被 Critic 以近乎相同措辞
  拒绝——"output structure is identical to the input structure with no real
  transformation"、"simply copy-pasting the entire raw text blob"、"blindly
  copy-pastes the raw input text verbatim"。三个不同工具概念的独立复现，不是同一工具
  的重试。
- **应对**：BUILD prompt 增加 passthrough 自检规则——产出前比对输出各字段与输入原文
  的逐字重叠度，某字段与输入子串重叠 >70% 判定为未转换，必须重写而非直接引用；
  SPEC 阶段要求"转换"类工具必须写出至少一个输入到输出的判别式操作（排序/筛选/打分/
  归类/重写），不能只写"结构化"这类描述性词。
- **推论**：F-005 揭示的"愿景式规格导致偷懒实现"在这里的具体形态是偷懒到了底线——
  算法深度描述不够机械时，模型选择的最省力路径不是编造（F-004/F-009），而是原样
  照搬输入。编造、补形状、照搬这三种偷懒模式共享同一根因：SPEC 对"转换"动作定义得
  不够可执行，模型就会退回到它能确定不出错的操作——什么都不做。

## F-012 · Ground-truth 拒绝后的重试会换壳但不换病灶——同一失败指纹在同一工具的连续尝试中原样复现

- **日期**：2026-07-11 · **状态**：观察中
- **模型**：deepseek-v4-pro（BUILD，Mode 3）；Playwright 无头浏览器地面真值门（非 LLM，见 F-001）
- **声明**：Mode 3 工具被 Playwright 地面真值拒绝（"DOM did not react to input"）后，
  BUILD 收到的重试反馈只有症状级数据（fields_filled / text_changed / 节点数），不含
  "哪一行 JS 没有绑定事件监听器"或"处理函数没有写回 DOM"这类机制级信息。结果：同一
  工具连续 4 次重试，DOM 节点总数从 34 变为 52（说明代码结构确实被重写，不是简单
  复制），但核心病灶（`text_changed` 恒为 `False`）原样复现了 4 次。
- **证据**：质量账本 2026-07-11 同一工具连续 4 条记录：
  `fields_filled=4, text_changed=False, nodes 34->34`（×3）、
  `fields_filled=4, text_changed=False, nodes 52->52`（×1）。
- **应对**：Playwright 探测器需要从"前后节点数对比"升级为机制级诊断——例如检测目标
  input 元素是否绑定了 change/input 监听器，若绑定了，监听器函数体是否实际写入了
  目标节点的 textContent/innerHTML；重试反馈应把这条诊断原文喂给 BUILD，而不是复述
  "DOM 没反应"这一症状描述。
- **推论**：地面真值门解决了"要不要相信模型自称做到了"（F-001），但还没解决"模型
  如何修复它做错的具体机制"——症状级反馈只能触发换壳式重写，机制级反馈才能触发
  针对性修复。这是 F-001 之后地面真值系统需要补的下一层，样本量仅 1 个工具、4 次
  尝试，需要更多独立事件才能从"观察中"升级为"确认"。
## F-013 · 自我修改流水线的写入路径需要与外部编辑同等的语法防护，两者不会自动共享

- **日期**：2026-07-12（事故）/ 2026-07-17（修复）· **状态**：确认

  拒绝写入）；提交信息记录"verified end-to-end with the exact 07-12 killer

  导入、内容保留；新增 10 个单测覆盖净化器与 guarded-write 的拒绝/接受矩阵。
- **应对**：任何"系统改写自己代码"的写入函数，防护必须内建在写入函数本身

  修改的调用路径天然不经过那个钩子。
- **推论**：F-007 指出"把 HTML/JS 塞进 Python 字符串是稳定的语法错误源"，这条

  "写入自己源码"的每一处，都应该被当成需要 ground truth 校验的边界，而不是
  信任内部调用。

## F-016 · 地面真值探针本身有验证盲区——只认文本输入，不认选择式交互

- **日期**：2026-07-24 · **状态**：确认
- **模型**：deepseek-v4-pro（生成，Design Alchemy 连续两天设计"从预设选项选一个语气/
  意图"的选择式工具）；探针本身是我们自己的 Playwright 脚本，非 LLM
- **声明**：`_browser_interactivity_check` 的填充逻辑只处理
  `textarea/input[type=text]/contenteditable`，从不处理 `<select>`、单选/复选框、
  或"选项卡片"类点选控件。当工具的真实交互模型是"点选一个选项"而非"打字"时，
  探针填不进任何输入（`fields_filled=0`），无论 JS 是否真的工作，`text_changed`
  永远是 False——这不是工具假，是**验证工具本身认不出这种真实的交互形态**。
  与此同时捕获到的控制台报错"Clipboard write permission denied"是无头浏览器
  沙盒本身对剪贴板 API 的限制，与代码正确性无关，若原样喂给模型当作"要修的
  bug"，会浪费一次重试在不可能修好的东西上。
- **证据**：2026-07-24 全天 5 次以上失败原因均为 `fields_filled=0`，且工具描述
  明确是"select an intent/tone from options"类选择式 UI；两条失败记录的
  `console_errors` 字段均为剪贴板权限错误，与"DOM 没反应"无因果关系。
- **应对**：探针新增选择式交互驱动——对 `<select>` 切换到非默认选项、勾选单选/
  复选框、点击 `[role=option]/.chip/.option/[data-value]` 等选项类元素，均触发
  `input`/`change` 事件后再判定 DOM 是否变化；同时新增
  `_is_environment_noise()` 白名单过滤已知的无头浏览器环境噪音（目前含
  clipboard），不再把环境限制误报成代码 bug。重试反馈加入"若交互模型是选择而非
  打字"的专项检查点。
- **推论**：给 AI 生成的产物设计"地面真值"验证器时，验证器自己的交互覆盖面
  必须至少覆盖被验证系统能设计出的所有交互形态——否则验证器的盲区会被系统
  当作"这类交互不存在"的假象，反而定向淘汰了某一类可能完全正确的设计。
  验证器本身也需要像被验证的代码一样接受"过度自信/覆盖不全"的审视。

## F-017 · 真正的可靠性分界线是"价值是否依赖算法深度"，不是输出格式

- **日期**：2026-07-25（基于 2026-06-27 ~ 07-24 共 311 次尝试）· **状态**：确认
- **模型**：deepseek-reasoner(R1) 写 SPEC、deepseek-v4-pro 写 BUILD、qwen3.7-max 评审
- **声明**：按输出格式统计 28 天全部尝试，通过率分布为——
  E 环境型 11%（1/9）、D 实时画布 8%（6/75）、A 文本分析 3%（6/184）、
  **B 多字段表单 0%（0/25）、F 生成器+内联编辑 0%（0/18）**。
  这推翻了 F-002 的"纯函数比 HTML 可靠"，并给出更本质的分界线：
  **工具的价值是否依赖对用户文本的深度分析**。
  - 依赖（评分、判断、提炼洞察）→ 约 3%，且通过者中一半带 Critic 标注的
    "没有真实算法深度"。原因是单文件、无模型、无语料的工具**真的做不了深度语言分析**。
  - 不依赖，价值在做工与在场感（可调的视觉、活的乐器、自己运行的器物）→ 8-11%，
    且不带瑕疵标注。因为这类工具的"深度"是交互与视觉的做工，模型确实能做。
- **证据**：`lili_ledger_report.py` 28 天聚合 + 按 format 字段分组统计（311 次尝试，
  13 次通过）；13 次通过中 7 次（54%）带 `[Shipped with minor flaw]`，其瑕疵原文包含
  "no real algorithmic depth"（3 次）、"does nothing the user couldn't do in 10 seconds"
  （2 次）、"a professional would be embarrassed"（1 次）——全部集中在分析型工具。
- **应对**：① B/F 两个零产出格式在 SPEC prompt 中禁用，并在 `validate_spec` 加确定性
  改写兜底（B→A、F→D），因为模型有无视格式指令的前科；② SPEC prompt 写入实测通过率
  与新的分界线，明确"若摩擦点能被一个做得好的器物解决，优先 D/E"；③ 该偏好与 RULE 16
  （物理世界情感基础）本就一致，现在有统计支持。
- **推论**：给自治生成系统做能力画像时，"输出格式"是表象维度，容易因早期小样本
  产生错误结论；真正需要测量的是**任务对模型薄弱能力（此处为深度语义理解）的依赖度**。
  同一个格式下，依赖度高的任务和低的任务表现可以差 3 倍。

## F-018 · 所有质量门都在检查"形式"，没有一道门检查"承诺"——工具能声称做 X 却完全不做 X 而全绿通过

  structured"通过，因为它看的是代码结构和输出格式是否工整，不是"承诺的事有没有
  发生"。持续 7 天无人发现，直到人工用真实场景手动测试。
- **证据**：`02_Toolbox/Design Alchemy/2026-07-28_SVG_Path_Purifier` 修复前 commit；
  人工复现：对含 `<g fill="none">` 的测试 SVG 跑 `process()`，输出中 `fill="none"`
  原样保留，且额外产生 `ns0:` 命名空间前缀污染（同一个 bug 的另一症状）。
- **应对**：SPEC 新增强制字段 `MUST_NOT_CONTAIN` / `MUST_CONTAIN`——要求对
  `TEST_INPUT` 的实际输出做出至少一条可机械核验的具体承诺（不能两者都为空）；
  `validate_tool()` 真实执行 `process(TEST_INPUT)`，用字符串包含检查核对承诺是否
  兑现，失败则精确报告"承诺删除的 X 还在输出里"或"承诺产出的 Y 没有出现"，
  而不是泛泛的"质量不足"。用真实的 SVG Purifier bug 模式写了端到端回归测试
  （`tests/test_promise_check.py`），证明修复前的代码会被新机制拦下、修复后的
  代码会通过。
- **推论**：验证链上的每一道门都在回答"这段代码/输出看起来怎么样"，没有一道门
  在回答"它做到自己说要做的事了吗"——这是两个完全不同的问题，前者可以无限打磨
  规则也测不出后者。**承诺与实现的核验必须是机械的、针对具体声明的，不能指望
  质量评分或代码审美类的检查顺带发现它。**

## F-019 · Harness 两处结构性改造：执行反馈内循环 + 差分测试（待生产数据验证）

- **日期**：2026-08-04 · **状态**：观察中（机制已实测验证，尚无生产运行数据）
- **模型**：deepseek-v4-pro（BUILD/自纠正）；两处改动均为 harness 侧机制，非模型能力发现本身
- **声明**：诊断此前的失败数据发现，311+ 次尝试里的失败集中在两类"人类看一眼就能
  发现"的问题：① 逻辑/语法/命名空间类 bug（F-018 SVG Purifier 是典型）——根因是
  BUILD **一次性盲写代码，写完前从未真正运行过**；② "输出不依赖输入"的泛化壳
  （占失败 32%，`fake-static`+`identical-output`+`generic-shallow` 三桶合计）——
  此前完全靠 Critic 的主观判断识别，没有机械证据。两个都不是"模型不够聪明"，
  是**harness 从未给模型机会看见自己的真实输出**。
- **应对**：
  ① **执行反馈内循环**（`self_correct_code`，`lili_pipeline.py`）：BUILD 写完代码后，
  在进入昂贵的 Critic/浏览器地面真值/质量评分之前，先本地做语法检查 + 真实执行
  `process(test_input)` + 核对 F-018 的承诺（MUST_CONTAIN/MUST_NOT_CONTAIN）。
  代码本来就没问题时零 API 调用（本地检查通过直接放行）；发现问题时把**真实观测到
  的输出/报错**（不是猜测）喂回去，最多 2 轮针对性修补，再进入完整验证链——完整
  验证链依然是最终把关者，这道内循环失败也不会让坏工具漏出去，只是让更多尝试
  "带着已经修好的代码"进入验证链。
  ② **差分测试**（`_differential_test`，`lili_validators.py`）：用两个刻意选择的、
  完全不相关领域的输入（科技裁员话题 vs 酸种面包话题）各跑一次 `process()`，
  和主测试输入的输出三方两两比对相似度（`difflib.SequenceMatcher`），全部
  >85% 相似则机械判定"没有真正处理输入"，给出量化证据（具体相似度百分比 +
  最长重复片段原文），而不是 Critic 的模糊印象。对执行失败的次要输入 fail-open
  跳过（不是所有工具都能吃任意英文段落，比如只接受合法 XML 的工具）。
- **证据**：`tests/test_self_correct.py`（7 个测试，覆盖零调用快速路径、语法/崩溃/
  承诺三类问题的检测与修补、二轮复检真的抓到"修了个寂寞"的补丁、最大轮次耗尽后
  优雅降级）、`tests/test_differential.py`（5 个测试，含用真实 fixture 跑通的
  端到端回归：模板壳工具被拒、真计算工具通过、次要输入崩溃时正确 fail-open）。
  95 个测试全绿，本地 3.13 与真实 3.11 环境双重验证。**尚未在生产流水线跑过一次**，
  本条目的"有没有用"结论要等明天起的真实运行数据。
- **推论（待验证）**：如果预测成立，逻辑类失败应该大幅减少（模型在提交前就看见并
  修好了），泛化类失败应该从"Critic 偶尔抓到"变成"每次都被量化证据抓到"。
  真正的风险是差分测试的两个固定对照样本可能对某些合法工具产生误杀（比如一个
  就该对大多数输入给出相似框架输出的工具），需要观察首周数据里有没有这类假阳性，
  必要时把阈值从 85% 调松或允许 SPEC 声明"本工具的合理相似度上限"。

## F-020 · 每周自进化的密封测试集 + 补丁式门槛（待生产数据验证）

  - 任何一项回测不通过，单独丢弃并记录原因（不是全批推翻），保留其余站得住的

  - 门槛还叠加了现有 108 个单元测试作为行为安全网（`run_test_suite()`）：测试套件

  - 通过门槛的旋钮写入 `lili_evolution_knobs.json`（纯数据文件，不是可执行 Python，

- **证据**：`tests/test_evolution_gate.py`（13 个测试，覆盖回测通过/拒绝/安全上限/

  + 差分测试有约 6 天干净的独立观察窗口，两者的生产效果不会互相混淆归因。
- **推论（待验证）**：如果设计成立，应该能观察到"提案被拒绝"本身成为一种有信息量

  与阈值。

## F-022 · "永不重复话题"+运行 190 多天，把选题结构性推向小众长尾

- **日期**：2026-08-03 · **状态**：观察中（机制已实测验证，尚无生产运行数据）
- **模型**：纯 harness/prompt 结构修复，不涉及具体模型能力发现
- **声明**：项目owner 直接指出最近很多选题"没有明确意义、难以标准化、不是大部分人的需求"，
  以手动触发跑出的真实案例为证——SPEC 选了"给发票上含糊的日期打标签，区分权责发生制/
  收付实现制报税用途"这样一个交互向导。诊断发现根因是两条规则叠加的结构性必然：
  ① FRICTION LOCK 要求"精确到具体的人和瞬间"；② 内存机制要求"绝不能重复过去做过的话题"。
  运行 190+ 天后，大部分人会遇到的通用摩擦点（会议记录整理、文字稿清理、批量改名）早就
  写过一遍，为了同时满足"新鲜"和"精确"，SCOUT 被迫的路径只剩往长尾钻——越挖越偏，因为
  中心地带已经写完了。"精确"被悄悄等同于了"小众"，而从来没有一道检验在管这两者的区别。
- **应对**：
  1. SPEC 新增强制字段 `COMMON_ROLES`（Rule 20）：要求列出 **至少 2 个明显不同的职业角色**
     （不是同一人设的变体，比如"自由摄影师"和"自由插画师"算同一人设）都会撞上这个精确的
     摩擦点。`validate_spec` 机械核验：少于 2 个角色、或角色本质重复（大小写/去空格后相同），
     直接打回，不进 BUILD——不依赖模型自己判断"这个够不够通用"（它显然判断不准，不然也
     不会选发票日期这种），而是逼它具体列出角色，列不出来就是硬证据。
  2. 把 SCOUT 提示词里"绝对不能碰过去做过的任何话题"的措辞从"话题级"松绑为"具体工具级"：
     只禁止字面重建同一个工具（同样的输入/输出/算法），明确告诉模型"重新用不同算法角度
     深挖一个通用类别（会议记录、文字稿清理、简报撰写）"是可以的，好过为了避免重复硬找一个
     没人做过但小众的新名词。
- **证据**：`tests/test_universality_gate.py`（8 个测试，覆盖 2 个/3 个不同角色通过、0 个/
  1 个角色拒绝、精确重复角色拒绝、字段解析的逗号切分/缺失默认空/"none"归零）。126 个测试
  全绿，本地 3.13 与真实 3.11 venv 双重验证。
- **推论（待验证）**：如果设计成立，接下来几周的选题应该能看到"围绕通用类别深挖"的比例
  上升，"手机截图整理""发票日期标签"这类窄众概念的出现频率下降。真正的验证要等生产数据——
  跟 F-019/F-020/F-021 一样是"机制已验证但效果未验证"的状态。一个需要留意的风险：
  `COMMON_ROLES` 本身是模型自己写的，如果模型学会"编两个听起来不同、其实还是同一类人"的
  角色来蒙混过关（比如"独立记者"和"自由撰稿人"），这道检验就会变成走过场——这是纯文本
  匹配无法完全防住的，需要观察后续台账里 COMMON_ROLES 的实际内容是不是在应付了事。

- **模型**：纯 prompt 文本修复，不涉及具体模型能力发现
- **声明**：owner 怀疑"最近几天连续休息是不是新加的机制太严"，诊断台账后发现拒绝原因
  全部是 Critic 判断的老失败类型（幻觉编造、缺少必填字段、原样照抄输入），跟 F-019~F-022
  新加的门槛无关。但诊断过程中发现一个真实、独立的问题：28 天台账里 Office
  Automation 占了 175/304 次尝试（58%），且**这三天（08-03~08-05）SCOUT 在完全自由选择的
  情况下，连续三天都选了 Office Automation**——F-021 加的类别拦截下限（`_apply_category_
  floor`）对此完全没有效果，因为它只能防止"类别被过度禁用导致被迫选剩下一个"，而这次根本
  没有任何拦截在起作用，是 SCOUT 主动、自愿选的。查了 SCOUT 提示词里 Office Automation 的
  类别描述文本，开头就是"ANY repetitive professional production task"——用"ANY"这个词
  把自己写成了唯一一个无边界的兜底类，另外三个类别的描述都是限定在具体生活领域（学习/
  创作/疗愈）。而且描述里的"transcript summarisers"跟 Education Evolution 重复，
  "research-to-outline / brief extractors"跟 Design Alchemy 的"brief writing / spec-
  handoff automation"重复——任何模糊的摩擦点，语义上都最容易落进这个描述最松、覆盖面
  最广的类别，跟拦截逻辑无关，是类别定义本身在结构性地吸走流量。
- **应对**：把 Office Automation 的描述从"ANY ... task"改写成跟另外三个一样具体、有边界
  的定义——收窄到"行政/后勤类事务性工作"（发票合同文书、日程协调、费用记账、文件命名整理、
  批量重命名、往来邮件模板），并显式排除跟其他类别重叠的项（"NOT transcripts... that's
  Education Evolution"、"NOT briefs... that's Design Alchemy"）。
- **证据**：`tests/test_prompts.py` 新增 `MissionAreaScopeTests`（3 个测试：确认不再包含
  "ANY repetitive"这种无边界措辞、确认显式排除了 transcript/podcast、确认显式排除了
  brief/handoff）。129 个测试全绿，本地 3.13 与真实 3.11 venv 双重验证。
- **推论（待验证）**：如果诊断成立，接下来几天 SCOUT 的类别分布应该会更均衡，Office
  Automation 的占比应该从 58% 明显回落。这跟 F-021 的类别下限修复是互补而非替代关系——
  F-021 防止"被迫选剩一个"，F-023 防止"自愿选最松的那个"，两种机制解决的是不同的失衡
  来源，此前只做了前者，后者才是这三天数据里真正在起作用的那个。
